DMTP ​

Overview ​

DMTP combines native multi-token prediction (MTP) with parallel drafting from the DFlash family. The parallel draft can use DFlash, DFlash2, or another DFlash-family variant. Native MTP proposes the first candidate, T1; the parallel draft uses that candidate and its MTP representation to propose the rest of the block. The target verifies the combined proposals.

The motivation is the accepted-prefix rule: if the first proposal is rejected, the rest of the block cannot be committed in that round. A target model's pretrained MTP module can provide a useful first proposal, while a small parallel draft provides a longer continuation at low additional drafting cost. DMTP combines these roles and passes the MTP predictor representation to the parallel draft. Its benefit depends on the target's MTP quality and the cost of the extra MTP step.

Start with speculative decoding for the common verification procedure. DFlash2 describes one of the parallel draft architectures that can be used inside DMTP.

How it works? ​

Source: the official DMTP blog, Figure 2. The diagram illustrates dual-anchor residual conditioning; the conditioning adapter and proposal layout are checkpoint-specific.

Let A be the last emitted token and T1 the next candidate. One round proceeds as follows:

  1. Run native MTP once. Given the aligned target state and token input, MTP predicts T1. Retain the hidden representation that produced T1.
  2. Condition the parallel draft. Provide T1 and its predictor state along with the normal target-context features. In the released residual adapters, the conditioning update is added only to T1's token embedding.
  3. Draft the remaining positions. A DFlash-family model predicts the continuation in parallel. In the 27B release, [A, T1, MASK × 6] yields seven proposals: T1 from MTP and six from DFlash2. A is already emitted and is not a new proposal.
  4. Verify the combined block. The target applies the runtime's speculative verification rules. Commit the accepted prefix and correction or bonus token, update caches, and repeat from the new verified context.

Why pass both a token and a hidden state? ​

T1 identifies the concrete first candidate. The MTP predictor state also contains information useful for continuing after it. The residual interface can be written schematically as

e~T1=eT1+f(eT1,stopgrad(hMTP)).

The function f is checkpoint-specific. It can project the MTP state through a low-rank network or combine separately normalized token and MTP features. The original token embedding remains available through the residual path. The released variants below use these different adapters.

Correct alignment matters: the predictor state for T1 is the state that generated T1, not the state obtained after consuming T1. The target context must also stop at the boundary expected by the checkpoint. These interfaces affect what the draft can read, so they belong to the training and serving contract rather than being interchangeable tensor shapes.

Training ​

The target and native MTP remain frozen while the parallel draft and its conditioning adapter are trained. In the released checkpoints, T1 is taken from the training sequence; at inference it is proposed by native MTP. The unknown continuation positions receive draft prediction supervision. The MTP predictor state is detached, so the draft loss does not fine-tune the target's MTP module.

For DMTP training, use the SpecForge implementation branch. Follow its training guide for capture-plugin setup, MTP feature preparation, and online or offline training. A Qwen3.6-27B example configuration is provided on that branch; update the model and dataset paths and server URL for your environment. The guide documents supported target architectures, dependencies, and feature-alignment requirements. Its example layout and fusion interface should be read alongside the checkpoint you intend to train.

Inference ​

DMTP adds an MTP step before parallel drafting. The runtime must coordinate the two proposal sources, use the corresponding proposal distributions for exact sampling, and commit or roll back their cache state after verification. An ordinary DFlash worker does not acquire this behavior merely by loading DMTP draft weights.

Performance should be measured over the entire cycle, including MTP, parallel drafting, selection, target verification, and cache management. Improving T1's acceptance can help later candidates become usable, but does not by itself guarantee higher throughput. Sampling settings, concurrency, and the model's native MTP implementation all affect the result.

Serving ​

Use a DMTP-aware runtime with the adapter matching the checkpoint. For 27B, follow the reference launch command in the model card or its serve_dmtp.sh. That reference uses the implementation branch and enables SGLANG_DMTP_T1_RESIDUAL=1.

For 120B, follow its model card and the implementation branch. It additionally requires the architecture-specific HC/QSA adapter. Its configuration defines its own query-slot and proposal layout; do not reuse the 27B launch settings.

These release-specific serving paths do not establish support in an unmodified SGLang release or in SpecForge's canonical SGLang exporter. See training and export for the current exporter support. Inference performance is still being optimized; consult the model cards for runtime requirements and validation status.
