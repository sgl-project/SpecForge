# LongSpark training (Qwen3-8B)

[LongSpark](https://arxiv.org/abs/2609.37029) is a draft-KV-free parallel
drafter. Each proposal reads a global memory that summarizes the whole target
prefix in a few learned slots, the most recent target K/V rows, and the selected
target hidden states, then predicts a block of tokens in parallel. The drafter
therefore does not keep its own growing KV cache.

This integration trains the full Qwen3-8B drafter (five decoder layers and a
rank-256 Markov head) with the standard SpecForge trainer, optimizer and
checkpoint lifecycle. See [RFC #976](https://github.com/sgl-project/SpecForge/issues/976)
for the design discussion.

Current scope:

- Target: Qwen3-8B (BF16, frozen).
- Features: online capture only, via the patched SGLang server with TP1/PP1.
  Offline feature files are not supported.
- Inference serving, other model sizes and ablations are out of scope.

## Data

Prepare conversations whose assistant turns were generated by the target
model. The example config uses the Qwen chat template, supervises every
assistant turn (`train_only_last_turn: false`) and truncates each conversation
to 4096 tokens. See [Data preparation](data_preparation.md) for the JSONL
format.

## Feature capture

In addition to hidden states, LongSpark needs the post-RoPE target keys and
values of the selected layers. Hidden-only feature caches from EAGLE3, DFlash or
DSpark cannot be reused. Apply the versioned capture patch and start eight TP1
servers with the `longspark` capture method. Set the Mooncake environment
variables and start Mooncake as described in the
[disaggregated training guide](disaggregated_training.md) before starting these
services and the trainer. The optional capture plugin does not export target
K/V yet; use the patch backend.

The example below runs one capture service and one trainer rank per GPU. This
placement was validated on eight 144-GB NVIDIA L20X GPUs; the static memory
fraction leaves GPU memory for the trainer. For other hardware, choose the
service placement and memory fraction to fit both processes.

```bash
bash scripts/apply_sglang_spec_capture_patch.sh

# 32 GiB per service, 256 GiB total host feature-store capacity.
export MOONCAKE_GLOBAL_SEGMENT_SIZE=$((32 * 1024 * 1024 * 1024))
mkdir -p outputs/qwen3-8b-longspark/capture
for gpu in {0..7}; do
  CUDA_VISIBLE_DEVICES="$gpu" python -m sglang.launch_server \
    --model-path Qwen/Qwen3-8B \
    --port "$((30000 + gpu))" \
    --nccl-port "$((31000 + gpu))" \
    --tp-size 1 \
    --dtype bfloat16 \
    --attention-backend fa3 \
    --mem-fraction-static 0.18 \
    --context-length 8192 \
    --max-running-requests 8 \
    --chunked-prefill-size -1 \
    --disable-cuda-graph \
    --disable-radix-cache \
    --enable-spec-capture \
    --spec-capture-method longspark \
    --spec-capture-aux-layer-ids 0 9 18 26 35 \
    > "outputs/qwen3-8b-longspark/capture/gpu${gpu}.log" 2>&1 &
done
```

Wait for all eight `/health` endpoints to succeed before starting training.
The explicit NCCL ports prevent simultaneous servers from choosing the same
rendezvous port.

Per-sample features:

| Feature | Shape |
| --- | --- |
| `input_ids`, `loss_mask` | `[1, tokens]` |
| `hidden_states` | `[1, tokens, 5 * 4096]` |
| `target_last_hidden_states` | `[1, tokens, 4096]` |
| `target_keys`, `target_values` | `[1, tokens, 5, 8, 128]` |

The last selected hidden state is taken after the final norm. KV rows are
copied out of the KV pool before SGLang can reuse that memory, and all features
travel through the existing Mooncake data plane.

## Training

```bash
FSDP_SHARDING=NO_SHARD specforge train \
  --config examples/configs/online/disaggregated/external/qwen3-8b-longspark-disaggregated.yaml
```

Update `model.target_model_path` and `data.train_data_path` for your
environment. The example uses eight data-parallel ranks, micro-batch 1 and 64
accumulation steps (global batch 512), with eight capture endpoints listed in
`deployment.disaggregated.server_urls`. The producer creates one capture worker
per endpoint; this count is a deployment setting and is independent of the
trainer world size. Capture services and Mooncake are started separately.

Key recipe settings:

| Setting | Value |
| --- | --- |
| Optimizer | AdamW with FP32 master weights, lr `6e-4`, betas `(0.9, 0.999)`, no weight decay |
| Schedule | 10 epochs, 4% warmup, cosine decay, gradient clipping at 1.0 |
| Anchors | Up to 512 distinct anchors per sequence (`training.num_anchors`) |
| Loss | `0.1 * CE + 0.9 * L1(teacher probs, draft probs)` over the full vocabulary (`training.dspark_ce_loss_alpha`, `training.dspark_l1_loss_alpha`) |
| Position weights | `exp(-k / 4)` for block position `k` (`training.loss_decay_gamma`; unset means uniform) |

Model geometry is set in `configs/qwen3-8b-longspark.json`: `block_size` (7),
`global_memory_slots` (16), `recent_kv_window` (256) and `target_layer_ids`.

The loss is normalized across data-parallel ranks for each micro-batch and then
averaged over accumulation steps.

Capturing target K/V needs much more store capacity than hidden-only capture.
The example bounds the in-flight queue at 512 samples; make sure the Mooncake
segments can hold at least one optimizer step of features.

## Tests

```bash
python -m unittest tests.test_algorithms.test_longspark \
  tests.test_runtime.test_longspark_capture -v
```

The tests cover registration, capture layout and buffer lifetime, anchor and
label offsets, the loss and its per-position gradient weights, weight loading
and export, and the resume contract. They run on CPU.
